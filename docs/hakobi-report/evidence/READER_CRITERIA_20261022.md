# ツール紹介レポート 読者評価基準（2026年10月22日）

評価者: 執筆担当と別のエージェント `technical_report_review`。本文・図の作成には参加せず、この評価票と評価記録だけを編集する。

## 評価の目的と手順

ユーザーが追加で「テスト失敗の報告や効果未測定の説明は不要で、ツールを作ったことが伝わる紹介にしたい」と指定したため、目的をツール紹介に変更した。旧基準と旧評価は `_BEFORE_SCOPE_CHANGE.md` に保存した。初読の読者が業務への使い道と最初の行動を説明できるかを判定する。技術的な裏付けは保つが、配布本文で品質審査を行う目的ではない。以下を改稿前後に固定して適用し、目標点に合わせた配点や採点の変更を行わない。各項目は達成した内容と不足を根拠に整数で採点する。高得点だけで導入効果や利用者満足を証明したとは扱わない。

| 軸 | 配点 | 満点の条件 | 参考となるER項目（適用範囲のみ） |
|---|---:|---|---|
| A 読者の困りごとと使う価値 | 20 | 冒頭で対象者・業務の困りごと・HAKOBIで行えることを言え、機能名を知らなくても使い道を理解できる | T-01、A-01、I-01〜04、C-03 |
| B 個人からチームへの利用像 | 15 | ひとりで始め、データを引き継ぎ、担当や相談を共有する流れが無理なく追える。モードとコピー・非同期の違いも正確 | I-03〜04、W-11、M-01 |
| C 最初の行動と資料の導線 | 15 | 読後に最初に試す操作、チーム化の準備担当、導入ガイドの所在、試用時の確認事項が分かる。本文内参照と配布物の導線が有効 | I-06、M-07、C-04、W-05 |
| D 具体例・図・読みやすさ | 15 | 使用場面、具体的な記録例、画面で見る点が近くにあり、図は読める。技術者が拾い読みしても本文の論旨を失わない | W-02〜09、W-13〜14、D-05 |
| E 技術的正確性と説明の連結 | 15 | 個人用・チーム用の機能、データ引継ぎ、通信と利用条件が実装と整合する。仕組みの説明が利用者の疑問に答え、紹介が仕様と矛盾しない | M-01〜06、W-11、R-05〜07 |
| F 主張の誠実さ | 10 | 機能・利用例・期待する使い方を分け、架空の実績や利用者の声を作らない。テストや実測効果に触れる場合だけその根拠を求める。失敗経緯や「効果未測定」の省略自体は減点しない | R-01〜04、R-06、C-05〜06 |

| 合計 | 100 |  |  |

90点以上を改稿の目標とする。ただし、重大な誤仕様、不実の品質合格の主張、根拠のない実測効果の断定、実在の利用者の声の捏造、致命的な出力崩れがある場合は得点にかかわらず要修正とする。表示を確認できない場合は本文評価と表示評価を区別し、出力合格を断定しない。

## 独立した読者役で答える質問

実在者のアンケートではなく、評価者が次の立場で本文から答えられるかを試す。

- メンバー: 自分のどの仕事に使いたいか。最初に何をするか。続ける負担や不安は何か。
- リーダー: 誰のどの状況をどう把握し、どの場面で相談するか。数字をどう解釈するか。チームで試す理由と留保は何か。
- 準備担当: 誰が何を準備し、どこを見て配置するか。個人データの扱いと運用制約を説明できるか。

本文から分からなければ推測で埋めず「不明」と記録する。最終稿では各軸の採点・根拠・未達点、3役の回答と留保、必須ゲート、評価対象と確認範囲を記録する。
