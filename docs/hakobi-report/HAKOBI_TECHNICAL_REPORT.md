# チームの仕事を見える化する業務管理ツール「HAKOBI」の設計と実装

## 日々の記録を、状況確認と定例・週報に生かす

作成日: 2026年10月17日
対象: 2026年10月17日時点のHAKOBI（デスクトップ版1.0.5、コミットf9c1bc6に8.2節の修正を加えたもの）

## 概要

係やグループで仕事を進めるとき、ほかの人の仕事がどこまで進んでいるかは、本人に聞かないと分からないことがある。定例や週報の前には、記憶をたどって別の一覧を作り、報告のたびに同じ内容を書き直す手間もかかる。この手間を減らし、チームの予定・担当・進捗を同じ画面で確かめられるようにするため、業務管理ツールHAKOBIを開発した。本レポートでは、2026年10月17日時点の実装について、設計、実装、品質の確認結果を報告する。

HAKOBIはガントチャートを中心に、作業の区切りに残した進捗率と進捗ログを、チームの状況確認、定例での相談、週報の下書きに使い回す。1人で使う個人用はElectronで作ったデスクトップアプリとして動く。チーム用は社内LAN（Local Area Network）に置いたサーバーへ、ブラウザとデスクトップ版から接続する。両者は同じReactの画面を共有し、データを読み書きする窓口だけを切り替える。チーム用にはWebSocketによる変更の通知、定例のための報告タブと定例モード、Microsoft 365 Copilotへ渡せるMarkdown形式の出力を実装した。

2026年3月に個人用として開発を始め、5月にチーム用を加えた。10月17日に型チェック4種とWebのビルドを実行し、すべて成功した。自動テストは、最初の実行で1コマンドが時間切れとなった。アプリの定期処理のタイマーがテストのプロセスの終了を妨げていたためで、これを直したあとは15コマンドすべてが合格した。10月9日の全体確認で見つけた13件の不具合は修正済みである。これらの結果から、目指した五つの姿に対応する機能を実装できたと判断した。導入による効果はまだ測っていない。今後は定例と週報にかかる時間などを測り、効果を確かめる。

# 1. 序論

## 1.1 背景

係やグループの仕事は、複数のメンバーが期限のある業務を分担して進める。メンバーの仕事の状況は本人に聞かないと分からないことがある。定例や週報の前には、期間中に何が進んだかを思い出しながら別の一覧を作る。報告のたびに、同じ内容を一から書き直すこともある。

こうした手間は、仕事の記録が報告の形で残っていないことから生じる。作業の区切りに短い記録を残し、それを確認や報告にそのまま使えれば、聞き直しや書き直しを減らせる。HAKOBIはこの考え方をチームの日常業務に取り入れるために開発した。

本レポートでいうガントチャートは、仕事を横棒で時間軸に並べ、開始日、期限、進み具合を示す図である。進捗ログは、仕事ごとに日付つきで積み上がる短い報告を指す。

## 1.2 HAKOBIの位置付け

HAKOBIは作業の区切りに残す記録を1か所に集め、チームの状況確認、定例、週報の準備に使う道具として位置付ける。使い方は二つある。表1に違いを示す。本文では1人で使う形を「個人用」、社内LAN（Local Area Network）のサーバーを複数人で使う形を「チーム用」と呼ぶ。チーム用にはブラウザから使う方法と、デスクトップ版から接続する方法（チーム接続）がある。

対象は個人用のデスクトップ版、チーム接続のデスクトップ版、ブラウザ版の画面、チーム用のサーバー、自動テストおよび運用文書である。内容は2026年10月17日時点の実装に基づく。

導入による効果（時間の短縮など）は、まだ測っていないため扱わない。インターネットへの公開、サーバーに接続できない間の編集と自動同期、複数のグループの同時利用、デスクトップ版の自動更新は、実装の範囲外である[I3]。利用者のPCやサーバーのOS（Operating System）が侵害された場合の対策も対象外とする。

# 3. 設計の考え方と全体構成

## 3.1 五つの設計方針

設計では次の五つを方針とした[I2]。

一つ目はガントチャートを中心にすることである。日程、担当、進捗、仕事の順序を一つの画面で確かめられるようにし、カンバンや報告などの画面は同じタスクを別の切り口で見せる。

二つ目は画面を一つにすることである。個人用とチーム用は同じReactの画面を使う。画面はデータベース（Database、DB）を直接扱わず、`window.api` という窓口を通して読み書きする。窓口の中身だけを、個人用ではIPC、チーム用ではHTTPとWebSocketの実装に切り替える。

三つ目は記録の役割を分けることである。タスクの「説明」には目的、「メモ」には今の状況を書き、「進捗ログ」には日付つきの報告を積み上げる（5.1節）。役割が決まっていると、同じ記録を確認にも報告にも使える。

四つ目は社内LANの中で軽く運用することである。サーバーは1つのプロセスで動き、データはSQLiteのファイルに保存する。別のDB製品を構築する必要はない。

五つ目はすでに使っている人を止めないことである。チーム用を加えた後も、個人用のデスクトップ版は動き続けるように保つ。サーバーが配信する画面とインストール済みのデスクトップ版は別々に更新されるため、新旧が混ざっても動くようにした（3.3節）。

## 3.2 構成要素

HAKOBIの構成を図2に示す。個人用では、デスクトップ版の中の画面がIPCでmainプロセスを呼び、mainプロセスがPC内のSQLiteを読み書きする。チーム用では、ブラウザとデスクトップ版の画面が同じサーバーへ接続する。デスクトップ版は、サーバーが配信する画面を表示したうえで、タイマー、通知、トレイなどの端末の機能を加える。デスクトップ版がサーバーのDBファイルへ直接接続することはない[I1]。

## 3.3 データの流れと同期

チーム用で、あるメンバーの変更がほかのメンバーの画面に届くまでの流れを図3に示す。画面で保存すると、変更した項目だけをHTTPでサーバーへ送る。サーバーはログインを確かめ、DBを更新し、変更履歴を残す。続いて、WebSocketで接続中の全員に「どの種類のデータが変わったか」を知らせる。知らせを受けた画面は該当するデータを取り直して表示する。

[[FIGURE:sync-flow]]

図3 チームでの変更が全員の画面に届くまで

通知に本文を載せないのは、受け取った画面が常にサーバーの最新の内容を表示するためである。WebSocketはサーバーと画面の間で双方向に通知を送るための通信規約である[E5]。

複数人が同時に使うと、古い応答や他人の更新と衝突する場合がある。画面は選んでいるタスクと要求の順番を確かめ、古い応答を表示しない。保存では編集した項目だけを送り、同じ項目がほかの人に先に変えられていないかをDBの更新時に確かめる。これらは10月9日の全体確認で見つけた不具合への対策として加えた（8.3節）。

サーバーが配信する画面とインストール済みのデスクトップ版は、別々に更新される。そのため、デスクトップ版に足した機能は画面から呼ぶ前に存在を確かめ、古い画面が送らない項目は送られない前提で扱う[I2]。

## 3.5 技術の選択

主な技術と、選んだ理由、代わりの案を表5に示す。

表5 技術の選択

[[TABLE-WIDTHS:1900,3800,3660]]

| 技術 | 選んだ理由（利点） | 代わりの案と、選ばなかった点 |
|---|---|---|
| Electron | デスクトップ版で、トレイ、OSの通知、全体のショートカット、小さなタイマーの窓を使える[E1] | ブラウザだけで作る案。端末の機能を使えず、計測や通知に気付きにくい |

# 4. チームの仕事を見える化する仕組み

この章では、G1「チームの仕事が見える」に対応する機能を説明する。

## 4.1 ガントチャート

ガントの画面の例を図4に示す。タスクとサブタスクを日程のバーで並べ、担当と進捗をバーの上に表示する。表示の単位は日・週・月・年から選べ、土日・祝日の列と今日の列を色で示す。チーム用では、担当者別に並べ替えることもできる[I1]。

[[FIGURE:gantt]]

図4 ガントの画面（デモのデータ）

バーの色は予定に対する遅れを示す。経過した日数の割合を「予定の進捗」とし、実際の進捗率との差を日数に換算する。差が設定の日数（既定は2日）以上なら「遅れ」として橙色にする。期限を過ぎたものは赤、開始前は灰色、それ以外は青で示す。土日・祝日を除いて数える設定もある[I1][I2]。色は入力された日程と進捗から計算した目安であり、遅れの理由は進捗ログや本人の話で確かめる。

## 4.2 依存関係の再計算

HAKOBIの依存関係は、前の仕事が終わってから次の仕事を始める関係（Finish to Start）を採用した。前後の間に待機日数を置くこともできる。依存関係はガントとタスク詳細のどちらからでも編集できる[I2]。

前の仕事の日程を変えると、後ろに続く仕事の日程を計算し直す。依存関係の追加、待機日数の変更、削除でも同じく再計算する。図5はAからBとCに分かれ、Dで合流してEへ続く例である。Aの期限を延ばすと、Cが後ろへずれ、Cの後に始めるDとその後ろのEも後ろへずれる。

[[FIGURE:dependency]]

図5 分岐と合流がある依存関係の再計算

当初の実装は同じタスクを一度しか計算しなかった。そのため、合流するDを、もう一方の枝の更新より先に計算すると、Dが古い日程のまま残った。10月9日の全体確認でこれを見つけ、すべての前工程を計算してから後工程を計算する順番に改めた[I4]。この計算は個人用とチーム用の両方のDBの層にあり、両方を同じ規則で直した。

Ctrl＋Kで移動・操作のパレットを開くと、タスク名、カテゴリ、担当者からタスクを探し、画面を切り替えられる。表示中の画面と選んだタスクはURL（Uniform Resource Locator）に反映するため、タスクのリンクをチャットに貼って共有できる。チーム用では、受け取った人も同じサーバーにログインすれば、そのタスクを開ける。

動作を軽くするため、ガント、一覧、詳細以外の画面は必要になったときに読み込む。計測中の経過秒数は表示する部品の中だけで数え、画面全体を毎秒描き直さない。ガントと一覧の行は、内容が変わらなければ描き直さない[I2]。

## 6.4 デスクトップ版のチーム接続

チーム接続のデスクトップ版には、ブラウザ版にない端末の機能を加えた。小さなタイマーの窓、進捗の素早い投稿、トレイとタスクバーからの計測の開始・切り替え・停止、OSの通知と未読バッジである[I1]。

通知を出すかどうかの判定は、表示していないメイン画面が行い、結果をデスクトップ版の本体へ渡す。本体はサーバーに直接問い合わせない。新着かどうかは端末に保存した前回の確認時刻で判定し、初めて接続したときには、既存の通知をまとめて出さないようにした[I2]。

# 7. 運用と安全の仕組み

この章では、G5「社内で軽く運用できる」に対応する仕組みを説明する。

## 7.1 アカウントと認証

チーム用のアカウントは管理者が発行し、利用者が自分で登録する仕組みは設けない。パスワードは6文字以上とし、bcryptでハッシュにして保存する。ログインの状態はCookieで保ち、有効期限の既定は30日である[I2]。各自のパスワードは設定の画面から変更できる。

管理者がメンバーを無効にすると、計測中のタイマーを止めて記録し、ログインと同期の接続を終了する。メンバーを削除するときは、担当を外し、作業ログ、投稿、変更履歴は残す。削除したログインID（Identifier）は再び使えない[I1]。

## 7.2 社内LANでの運用

サーバーは社内LANのPCに置き、Windowsサービスとして登録して常時動かせる。既定のポートは4577である。グループごとにデータを分ける場合は、グループごとにサーバーのプロセスを立て、ポート、データの保存先、Cookieの名前を分ける。ポート番号を変えるだけではDBは分かれない[I3]。

## 7.3 バックアップ

サーバーは起動時と1分ごとの点検で、その日のバックアップがなければ取る。バックアップは1日1つで、既定では14日分を残して古いものから消す。管理者は設定の画面から、現在のDBを1つのファイルとしてダウンロードできる。SQLiteはWALで書き込むため、動いている間にDBのファイルだけをコピーすると、直近の更新が欠けることがある。自動バックアップとダウンロードには、SQLiteのバックアップ機能を使う[I3]。復元は画面からは行わず、サーバーを止めてファイルを置き換える手順を運用ガイドに定めた。

## 7.4 デスクトップ版の配布

デスクトップ版のインストーラーは、サーバーの「/download」ページから入手できる。このページはログインなしで開ける。サーバーは、配布フォルダの`latest.yml`に書かれたインストーラー1つだけを配る。ファイル名、サイズ、SHA-512（Secure Hash Algorithm 512-bit）の値が一致しないものは配らない[I2]。

公開は専用のコマンドで行い、インストーラーを先に置き、`latest.yml`を最後に置き換える。コピーの途中のファイルが配られることはない。新しいバージョンを公開するとデスクトップ版の画面にお知らせが出るが、インストールは各自が行う[I3]。

## 7.5 個人用データの取り込み

個人用で作ったタスクは、管理者がチーム用へ取り込める。取り込み先のメンバーを選び、まず「ドライラン（確認のみ）」で件数を確かめてから実行する。タスク、サブタスク、依存関係、作業ログ、予定、進捗ログと返信、変更履歴を引き継ぐ。取り込みは個人用からチーム用へのコピーであり、再び実行しても取り込み済みのデータは更新しない。取り込んだ後も、個人用とチーム用のDBは同期しない。

# 8. 品質の確認

## 8.1 確認の方法

品質は型チェック、ビルド、自動テストの三つで確かめた。

型チェックでは、TypeScriptのコンパイラーで、mainプロセス、共通の画面、Webの窓口、サーバーの4つを検査する。窓口の左右の対応（3.2節）もこの段階で確かめられる。ビルドでは、Webの画面を一時フォルダへ出力し、本番用の組み立てが成功することを確かめる。

自動テストはNode.jsで実行するスクリプト36ファイルと、Node.jsのテストランナーで実行するテスト12ファイルからなる。テストはそれぞれ独立した一時DB、一時フォルダ、一時サーバーを使い、運用中のDBやサービスに触れない。画面の動作は実際のElectronを表示せずに起動して確かめる[I3]。対象は保存先の変更、削除、依存関係の再計算、同時編集、タイマー、認証、取り込み、配布、進捗ログ、保留、ToDoリスト、ガントの表示位置などである。

## 9.2 画面を一つにしたことの利点と代償

画面を一つにしたことで、機能を一度作れば個人用とチーム用の両方で使える。利用者は個人用で使い方を覚え、そのままチーム用へ移れる。窓口の左右の対応は型で強制されるため、片方だけの機能が残りにくい。

一方で、代償もある。データの型は、mainプロセスと画面にそれぞれ定義があり、同じ構造に保つ必要がある。依存関係の再計算のように、同じ規則を個人用とチーム用の両方のDBの層に持つ処理もある。8.3節の再計算の不具合は、両方で同時に直す必要があった。新旧の画面が混ざる前提の設計も欠かせない。これらは変更のたびに両方を確かめるテストで補っている。

## 9.3 SQLiteと1台のサーバーの利点と限界

SQLiteを選んだことで、別のDB製品を構築・保守する負担を省けた。データはファイルとして扱えるため、バックアップと復元の手順も単純になる。SQLiteでは、1つのDBファイルに同時に書き込めるのは1つの処理だけである[E4]。WALにより読み取りと書き込みは互いを妨げないが[E3]、書き込みが非常に多い使い方には向かない。HAKOBIは1つのサーバーで6人程度の利用を想定しており、この範囲では書き込みの集中は起きにくいと考える。規模を大きく超える場合は、グループごとにサーバーを分けるか、DB製品の利用を検討する。

サーバーが止まると、チーム用ではタスクや進捗を保存できない。進捗の下書きは端末に残り、再接続した後に投稿できる[I3]。復旧に備え、サーバーをWindowsサービスとして動かし、1日1回のバックアップを取る。

## 9.4 安全性についての判断

チーム用は社内LANでの利用を前提とし、通信はHTTPで行う。HTTPは通信を暗号化しないため、LANの中で通信を盗み見られた場合、内容やログインのCookieが読まれるおそれがある。社内LANの外へは公開しない前提で現在の構成としたが、HTTPS（Hypertext Transfer Protocol Secure）による通信の暗号化は今後の課題とする。

パスワードの保存にはbcryptを使い、計算の重さを表す係数は10とした。OWASP（Open Worldwide Application Security Project）の指針は、新しいシステムにはArgon2idを勧め、bcryptを使う既存のシステムには係数10以上を求めている[E2]。HAKOBIの設定はこの下限を満たすが、方式とパスワードの最小の長さ（6文字）は見直しの候補とする。パスワードを変えたときに既存のログインを終了するかどうかも、まだ決めていない[I4]。

カテゴリの「集計外」は集計の対象を分ける設定であり、ほかの人から見えなくする設定ではない。チームのタスクは、メンバー全員が見られる。見せたくない情報を書く場所としては使わないよう、利用者に伝える必要がある。

# 10. 結論と今後の展望

## 10.1 結論

HAKOBIはチームの予定・担当・進捗を同じ画面で確かめ、作業の区切りに残した記録を定例と週報に使い回すための業務管理ツールである。

個人用とチーム用は同じ画面を共有し、データの窓口だけを切り替える構成とした。チーム用では、変更をWebSocketで知らせて全員の画面を最新に保ち、古い応答や同時編集による上書きを防いだ。ガントと依存関係の再計算、チーム画面、進捗ログと要相談で仕事を見える化し、報告タブ、定例モード、報告のリマインド、Markdownの出力で記録を定例と週報につないだ。計画、タイマー、ToDoリスト、デスクトップ版の通知で、一人ひとりの日常業務も支えた。運用では、管理者によるアカウントの発行、自動バックアップ、検証つきの配布を用意した。

型チェックとビルドはすべて成功した。自動テストは、時間切れの原因となったタイマーを直したあと、15コマンドすべてが合格した。10月9日の全体確認で見つけた13件の不具合は修正した。以上から、目指した五つの姿に対応する機能を実装できたと判断する。

全体確認からは、既存の自動テストが通っていても、分岐と合流がある依存関係、保存先の変更、古い応答、同時編集の不具合が残りうることが明らかになった。個人用とチーム用で同じ規則を持つ処理と、複数人が同時に使う場面は、再現条件を決めたテストで確かめる必要がある。また、動き続けるアプリに加えた定期処理のタイマーは、同じコードを読み込むテストのプロセスの終了を妨げることがある（8.2節）。

## 10.2 業務への貢献

チームの仕事の状況を、本人に聞かずに画面で確かめられるようになった。定例と週報の材料を日々の記録から取り出せるため、報告のための書き直しを減らす下地ができた。週報の下書きをCopilotで作る流れは、日々の記録を生成AI（Artificial Intelligence）の入力として使う例でもある。個人用から始めてチーム用へ移れること、グループごとにサーバーを分けられることから、ほかの係やグループへ広げる際の基盤としても使える。

## 10.3 今後の展望

次の順に進める。

1. 表10の指標で効果を測る。定例の所要時間、週報の作成時間、報告なしの割合、期限超過の件数を、導入の前後で比べる。
2. 通信の暗号化（HTTPS）、パスワードの方式と最小の長さ、パスワード変更時のログインの扱いを見直す。
3. ほかの係やグループへ広げるため、サーバーの準備、アカウントの発行、個人用データの取り込みの手順を整える。

# 付録C 週報用エージェントの指示の例

Microsoft 365 Copilotで週報用のエージェントを作るときに、指示欄に保存する文の例を示す[E7]。係で使う週報の書式が決まっていれば、見出しや長さを合わせる。

```text
あなたは係内の週報の下書きを作成する担当です。
今回の依頼に貼り付けられたHAKOBIの報告Markdownと、依頼者が明示した補足だけを根拠にしてください。

最初に対象期間と担当範囲を確認してください。不明な場合は確認を求め、推測で埋めないでください。
業務ごとに内容をまとめ、次の見出しで簡潔な日本語の週報を作成してください。
1. 今週の主な実施内容
2. 継続中の仕事と現在の状況
3. 相談事項と保留中の仕事
4. 次に行うこと
5. 提出前に確認すること

担当者、期限、進捗率、保留の理由は、記録の内容を保ってください。
期間中の進捗の変化と現在の進捗率を混同しないでください。
要相談の記録と返信を読み、解決したと確認できない内容を解決済みにしないでください。
「期間内の記録なし」を「実施していない」という意味に受け取らないでください。
次の作業は記録に明示されたものだけを挙げ、来週の予定や成果を創作しないでください。
足りない情報や食い違いは「提出前に確認すること」に分けてください。
同じ内容は重複させず、業務名と具体的な動きが伝わる文章にしてください。
```
