方針

最初に結論：画面ではなく「細い1本」を作る

Webアプリを作るとき、先に全画面を描くのではなく、まず1件のタスクを入力し、保存し、再読み込みしても残るところまでを縦に貫通させます。これを「縦切り」や vertical slice と呼びます。

最初に入れるもの

  • タイトル入力
  • 追加ボタン
  • タスク一覧
  • GET / POST のAPI
  • Todosテーブル1個

最初は入れないもの

  • ログインと権限
  • WebSocket
  • ドラッグ操作
  • 繰り返し・通知・集計
  • Electronとの共通化
基礎知識

Webアプリを構成する5つの役者

「Webアプリ」という一つのプログラムがあるように見えますが、実際には役割の違うプログラムが協力しています。C#経験者なら、UI・Controller・Service・Repository・DBを別層に分ける感覚に近いです。

1. ブラウザ

HTMLを構造、CSSを見た目、JavaScriptを動作として実行します。Reactも最終的にはブラウザで動くJavaScriptになります。

2. フロントエンド

入力を受け、状態を持ち、画面を再描画します。このアプリでは React + TypeScript です。

3. HTTP API

フロントとサーバーの約束です。URL・メソッド・JSONの形・ステータスコードを決めます。

4. サーバー

認証、入力検証、業務ルール、DB操作を担当します。このアプリでは Express + TypeScript です。

5. データベース

ブラウザを閉じても残す情報を保存します。このアプリではファイル型DBの SQLite です。

+ WebSocket

サーバーからブラウザへ変更を知らせる常時接続です。最初からは不要で、複数人同期の段階で追加します。

技術選定

フレームワークはどう選ぶか

最適解は言語の好みだけでなく、誰が保守するか、リアルタイム性、配布方法、既存コードの有無で決まります。このアプリを学ぶ目的なら現行構成を使うのが自然ですが、C#中心のチームなら別案も十分に合理的です。

候補向いている状況長所注意点今回
React + TypeScript
Express + SQLite		現行アプリを理解・拡張したい既存コードを直接読める。UI部品とWeb/Electronを共有しやすいJavaScript系の非同期・Nodeの作法を学ぶ必要採用済み
ASP.NET Core
+ React		C#でサーバーを書き、豊かなUIも欲しいController/DI/EF Coreが使える。C#経験を活かせるフロントは結局TypeScript。2言語構成新規作成なら有力
ASP.NET Core
Razor Pages		フォーム中心で、JSを少なくしたいC#中心、仕組みが単純、初学者に優しい高度なドラッグやガントUIは追加JSが必要最初のCRUD教材に良い
Blazorクライアント側もC#を優先したい型とC#知識を共有しやすい現行React資産を再利用できず、求人・ライブラリ事情も確認が必要別プロジェクト向け
Next.js公開サイト、SSR、クラウド運用まで統合したいReactのフルスタック機能が揃う社内LANの小規模アプリには概念が増えやすい今回は過剰

このアプリで現行スタックを選ぶ理由

  1. ガント、ドラッグ、複数パネルなど、ブラウザ内の状態が多いのでReactが合う。
  2. TypeScriptにより Todo やAPI引数の形をコンパイル時に確認できる。
  3. 6人規模・社内LAN想定なので、運用が軽い Express + SQLite で十分。
  4. Electron版もReact画面を使うため、画面部品を二重に作らずに済む。
初心者への推奨このリポジトリを教材にするなら React + TypeScript + Express + SQLite。Web一般を最短で学びたいC#経験者なら、最初の1週間だけ ASP.NET Core Razor Pages でCRUDを作るのも良いです。ただし途中で技術を混ぜず、ひとつの小作品を完成させてから比較します。

PHASE 2

ブラウザ内CRUD：状態が変わる感覚をつかむ

CRUDは Create（作成）、Read（読取）、Update（更新）、Delete（削除）の頭文字です。まずReactのメモリ内だけで完成させます。再読み込みすると消えて構いません。

type Todo = { id: string; title: string; done: boolean }

const [title, setTitle] = useState("")
const [todos, setTodos] = useState<Todo[]>([])

function addTodo() {
  if (!title.trim()) return
  setTodos(current => [
    ...current,
    { id: crypto.randomUUID(), title: title.trim(), done: false }
  ])
  setTitle("")
}

function toggleTodo(id: string) {
  setTodos(current =>
    current.map(todo => todo.id === id ? { ...todo, done: !todo.done } : todo)
  )
}

Reactの状態更新で守ること

  • 配列に直接 push せず、新しい配列を作る。
  • 入力欄は value={title} と onChange をセットにする。
  • map で一覧を描き、各要素に安定した key={todo.id} を付ける。
  • 表示用の絞り込みは、可能なら元データを書き換えず filter で計算する。

練習課題

  1. 追加
  2. 完了/未完了の切替
  3. 削除
  4. 未完了だけ表示
  5. 空タイトルをエラー表示

完成条件：ページを再読み込みするまでは、追加・完了・削除が正しく動く。

PHASE 3

HTTP API：画面とサーバーを分離する

Expressサーバーを作り、最初はサーバーの配列に保存します。ここでは「通信」を理解することが目的なので、DBはまだ足しません。

// server/src/index.ts — 学習用の最小例
import express from "express"
import crypto from "node:crypto"

const app = express()
app.use(express.json())

const todos: { id: string; title: string; done: boolean }[] = []

app.get("/api/todos", (_req, res) => res.json(todos))

app.post("/api/todos", (req, res) => {
  if (typeof req.body.title !== "string" || !req.body.title.trim()) {
    return res.status(400).json({ error: "タイトルは必須です" })
  }
  const todo = { id: crypto.randomUUID(), title: req.body.title.trim(), done: false }
  todos.push(todo)
  res.status(201).json(todo)
})

app.listen(4577, () => console.log("http://localhost:4577"))
// フロント側
async function loadTodos() {
  const response = await fetch("/api/todos")
  if (!response.ok) throw new Error("読込に失敗しました")
  setTodos(await response.json())
}

async function addTodo(title: string) {
  const response = await fetch("/api/todos", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title })
  })
  if (!response.ok) throw new Error((await response.json()).error)
  await loadTodos()
}
CORSより開発プロキシフロントが5273、サーバーが4577ならオリジンが違います。現行の vite.web.config.ts は /api と /ws を4577へ代理転送します。初心者はまず同じ方式を使うと混乱が減ります。

完成条件：Network欄にGET/POSTが見え、サーバーを止めると通信エラーになる理由を説明できる。

PHASE 4

SQLite：再起動しても残るようにする

サーバー配列をSQLiteへ置き換えます。SQLをReactから直接実行してはいけません。ブラウザ → API → DB層の順を守ります。

CREATE TABLE IF NOT EXISTS Todos (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  done INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);
// DB層の考え方（better-sqlite3）
const insertTodo = db.prepare(
  "INSERT INTO Todos (id, title, done, created_at) VALUES (?, ?, 0, ?)"
)

export function createTodo(title: string) {
  const id = crypto.randomUUID()
  const now = new Date().toISOString()
  insertTodo.run(id, title, now)       // 値は ? に渡す
  return db.prepare("SELECT * FROM Todos WHERE id = ?").get(id)
}

ここで覚えるDB原則

  • 主キー：行を一意に識別するID。
  • 外部キー：別テーブルのIDを参照する関係。
  • 制約：NOT NULL や UNIQUE で壊れたデータを防ぐ。
  • トランザクション：複数更新を全部成功または全部失敗にする。
  • プレースホルダー：文字列連結でSQLを作らず、? に値を渡してSQLインジェクションを防ぐ。
  • マイグレーション：既存データを保ったまま列・テーブルを増やす手順。

完成条件：サーバーを停止・再起動してもタスクが残り、DBファイルの場所を説明できる。

PHASE 5

ガント：まず日付を幅に変換する

ガントは魔法の部品ではなく、日付の差をピクセルへ変換した横棒です。最初はドラッグなし、依存線なしで表示だけ作ります。

const DAY_WIDTH = 32
const msPerDay = 24 * 60 * 60 * 1000

function diffDays(from: Date, to: Date) {
  return Math.round((to.getTime() - from.getTime()) / msPerDay)
}

const left = diffDays(viewStart, taskStart) * DAY_WIDTH
const width = (diffDays(taskStart, taskEnd) + 1) * DAY_WIDTH

実装順

  1. 横軸の日付ヘッダー
  2. 1タスク1行
  3. 日付からバー位置を計算
  4. 今日線
  5. ズーム
  6. ドラッグ移動
  7. 左右端のリサイズ
  8. 依存線
  9. 循環チェックと後続日程の再計算
日付の落とし穴YYYY-MM-DD の日付だけを扱う処理と、時刻・タイムゾーンを持つISO日時を混ぜないこと。現行実装は日付キーを正規化するヘルパーを持ちます。ガントの日数計算は特に、夏時間のある地域で24時間割り算だけに頼るとずれることがあります。

完成条件：開始日と終了日を変えるとバー位置と幅が変わる。ドラッグは次の小目標に分ける。

起動処理

開発時と本番時で何が起きるか

開発時：2プロセス

# ターミナル1
npm run dev:server   # :4577

# ターミナル2
npm run dev:web      # :5273

ブラウザは5273へアクセス。Viteが /api と /ws を4577へ転送します。コード変更は即時反映されます。

本番時：1プロセス

npm run build:web     # dist-web/
npm run start:server # :4577

Expressが dist-web の静的HTML/JS/CSSとAPIの両方を同じ4577で配信します。

サーバー起動の正確な順序

  1. server/src/index.ts が initDb() を呼ぶ。
  2. DBフォルダを作り、SQLiteを開き、WAL・外部キーを有効化。
  3. テーブル作成、既存DBのマイグレーション、既定設定を挿入。
  4. 期限切れSessionを掃除し、ユーザー0人なら管理者を作る。
  5. express.json、Cookie解析、ユーザー付与middlewareを登録。
  6. health、auth、users、dataのrouteを登録。
  7. dist-web があれば静的ファイルを配信。
  8. HTTPサーバーにWebSocketを追加し、4577で待ち受ける。
なぜ server/package.json が別にあるのかbetter-sqlite3 はネイティブモジュールです。Electron用ABIと通常のNode.js用ABIが異なるため、依存フォルダを混ぜない設計です。これは単なる整理ではなく、実行環境の互換性を守る境界です。

永続化

データベースを「機能の関係図」として読む

現行サーバー版のスキーマは server/src/db/schema.ts にあります。最初に中心の6テーブルを理解し、その後に進捗・通知系を読みます。

テーブルを分ける理由

  • RunningState は「現在1件だけの状態」、WorkLogs は「確定した履歴」。意味が違うため分ける。
  • TodoCoAssignees は一つのTodoに複数ユーザーを付ける中間テーブル。
  • UserSettings はテーマなどユーザー固有、Settings は全体設定。
  • TodoChangeLogs は上書き前後を残し、進捗レポートに使う。

現行DBの安全策

  • journal_mode = WAL で読書きの並行性を改善。
  • foreign_keys = ON で参照整合性を有効化。
  • ON DELETE CASCADE で親削除時に従属行を整理。
  • 更新・依存連鎖・繰り返し生成などをtransactionでまとめる。
  • 起動時migrationを冪等に実行し、古いDBへ不足列を追加。
認証

ログインはパスワードを毎回送る仕組みではない

401と403の違い

  • 401 Unauthorized：ログインが必要、Sessionがない・期限切れ。
  • 403 Forbidden：ログイン済みだが管理者権限などが足りない。

現行実装で行っていること

  • bcrypt（cost 10）でパスワードハッシュを保存。
  • 32byteのランダムSession tokenを生成。
  • CookieをHttpOnlyにし、JavaScriptから直接読めないようにする。
  • WebSocket接続時も同じCookieで認証。
  • 初回ユーザー0人なら管理者を自動作成。
  • 管理者が自分自身を無効化・降格できないようガード。
インターネット公開時は追加対策が必要現行は社内LAN前提です。外部公開するならHTTPS、Secure Cookie、CSRF方針、rate limit、強いパスワード規則、監査ログ、秘密情報管理、脆弱性更新、バックアップ暗号化などを設計し直します。
同期

WebSocketは「変更通知ベル」として使う

WebSocketでは接続中のブラウザへサーバーから送れます。現行アプリは複雑な差分データを直接配らず、{ type: 'data:changed', scope: 'todo' } のような小さな通知だけを送ります。

長所

  • 実装と整合性が分かりやすい
  • 取りこぼしても再取得で最新になる
  • 画面側の既存load関数を再利用できる

代償

  • 変更ごとに一覧APIを再取得する
  • 大規模データ・大人数では通信量が増える
  • 同時編集の競合解決は別途必要

接続ライフサイクル

  1. AuthGate が /auth/me でログイン確認。
  2. 認証済みの間だけ connectRealtime()。
  3. web/lib/client.ts が現在のhostの /ws へ接続。
  4. サーバーがCookieを検証し、Client集合へ追加。
  5. presence、data changed、notification changedを受信。
  6. 切断時は段階的に再接続。ログアウト時は明示切断。
初心者が追加するタイミング同じCRUDを2つのブラウザで手動更新して正しく使えるようになってから追加します。WebSocketはデータ保存先ではなく、最新データを取りに行くきっかけです。
業務ルール

ガント依存関係はサーバー側で守る

現行は Finish to Start（先行タスクが終わってから後続開始）です。表示だけでなく日程の整合性を守る処理なので、Reactだけに置かずDB層でも実行します。

server/src/db/todos.ts の処理

  1. dependencyCreatesCycle：BFSで後続をたどり、追加予定の先行へ戻るか確認。
  2. enforcePredecessorConstraints：複数の先行から最も遅い必要開始日を選ぶ。
  3. shiftTodoToStart：期間の長さを維持してタスクを移動。
  4. resolveDependencyCascade：後続へ再帰し、連鎖更新。
  5. 依存追加・待機変更・Todo更新をtransaction内で実行。
削除時の仕様判断依存線を削除したとき、現在の実装は制約を再評価しますが、タスクを自動で過去へ戻すとは限りません。「制約を外す」と「以前の日付へ巻き戻す」は別の業務ルールです。仕様を文章で決めてから実装します。
