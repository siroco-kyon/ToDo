# タスク一覧簡素化・担当者別概要 実装プラン

更新日: 2026-08-28
状態: 要件整理・実装計画のみ（プログラム未変更）

この文書を今回の変更の基準とし、実装・検証・PRレビュー時に常に参照する。過去の `usability-improvement-plan.md` にある「複数選択と一括編集」は、本プランによって撤回されたものとして扱う。

## 1. 確定した要望

1. タスク一覧の複数選択と一括編集を撤去する。
   - 各タスクの通常の選択、詳細編集、完了、タイマー、並べ替え、アーカイブ等は残す。
2. 既存の担当者フィルターを概要にも反映する。
   - 「全員」「特定メンバー」「未割り当て」の範囲に応じて、概要の件数・進捗・要注意タスク等を切り替える。
3. 概要内のタスクに担当者名を表示する。
   - 主担当とサブ担当を区別できるようにし、担当者がいない場合は「未割り当て」と表示する。
4. 担当者フィルターが「全員」のとき、メンバーごとの活動をまとめて表示する。
   - 誰が、何を、どの程度行ったかを比較しやすい構成にする。
5. 用語は「ゴミ箱」ではなく「アーカイブ」に統一する。
   - アーカイブは削除ではないため、ボタン、ツールチップ、確認、Toast、絞り込みチップを含め「ゴミ箱」という表記を残さない。

## 2. 現状と問題点

- 一覧の担当者フィルターは、主担当またはサブ担当に選択メンバーが含まれるタスクを絞り込めている。
- 概要コンポーネントには絞り込み済みタスクが渡される一方、概要APIは条件なしでチーム全体を再集計している。このため、カードの件数や要注意一覧は担当者フィルターと一致しない。
- 概要の「今週やったこと」は別APIから取得しており、サーバー版ではログイン中ユーザーの作業ログだけになる。ほかの概要指標がチーム全体であることと表示範囲が一致していない。
- 概要APIのタスク項目には担当者ID・氏名・色・サブ担当が含まれていない。
- 既存の進捗レポートAPIには、メンバー別にタスク追加、完了、サブタスク追加、変更、進捗投稿、コメント、作業時間を返す仕組みがある。新しい集計を重複実装せず、この契約と集計ロジックを再利用できる。
- タスク一覧には選択チェック、選択状態、一括更新・今日へ追加・アーカイブ等の処理があり、利用頻度に対して画面と実装が複雑になっている。
- 現在、一部のツールバー、Toast、絞り込み表示に「ゴミ箱」という表記が残っている。

## 3. 表示範囲の仕様

概要の見出し直下に現在の対象（例: `対象: 全員`、`対象: 田中`、`対象: 未割り当て`）を表示する。担当者の選択元は既存フィルターを唯一の状態として使い、概要専用の独立した選択状態は作らない。これにより、一覧と概要で選択がずれることを防ぐ。

| 担当者フィルター | タスク系の集計・一覧 | 活動系の表示 |
| --- | --- | --- |
| 全員 | チームで閲覧可能な全タスク | メンバー別活動サマリーを全員分表示し、チーム合計も表示 |
| 特定メンバー | その人が主担当またはサブ担当のタスク | その人自身が行った活動の詳細を表示 |
| 未割り当て | 主担当がなく、サブ担当もいないタスク | 人に紐づく活動集計は出さず、「未割り当てタスクにはメンバー活動集計はありません」と説明 |
| Electron単独版 | 従来どおり端末内の全タスク | 「自分」の活動として従来相当を表示。空のユーザー一覧でも壊れない |

重要な区別:

- タスク系は「誰が担当しているか」で絞る。
- 活動系は「誰が実際に操作・記録したか」でまとめる。
- ある人が他人の担当タスクへコメントした場合、タスクの担当集計では担当者側、活動サマリーではコメントした人側に現れる。
- `個人／全体` の閲覧レンズとプライベートカテゴリの扱いは既存仕様を維持し、全体レンズでは非公開データを集計・表示しない。

## 4. 画面設計

### 4.1 タスク一覧

- 各行の複数選択チェックを削除する。
- 選択件数と一括操作バーを削除する。
- 通常クリックによる詳細表示、ドラッグ並べ替え、完了、タイマー、アーカイブ、復元、完全削除は維持する。
- チェック領域がなくなった分、タイトルの表示幅を確保する。

### 4.2 概要ヘッダー

- 現在の担当範囲を、メンバー色付きのラベルで明示する。
- 既存の担当者フィルターを変更すると概要を再取得し、読み込み中も直前の内容と対象名を混同させない。
- 無効化されたユーザーを過去データの表示対象から勝手に除外しない。既存フィルターで選択できる場合は氏名に「無効」を付ける。

### 4.3 概要のタスク表示

- 「期限が今日」「完了間近」「高優先度」「停滞」「要注意」等の各タスク行へ担当表示を追加する。
- 主担当は氏名と色付きドット、サブ担当は補助ラベルで表示する。人数が多い場合は先頭数名と `+N` に畳み、ホバーまたはタイトルで全員を確認できるようにする。
- 担当者がいないタスクは `未割り当て` と明示する。
- 「今週完了したサブタスク」にも親タスクの担当者を表示する。サブタスク自身に担当者が設定されている場合は、親担当とは分けてサブタスク担当を優先表示する。

### 4.4 メンバー別活動サマリー

「全員」選択時は、既存の「今週やったこと」をチーム合計とメンバー別カードに再構成する。

各メンバーカードの最低表示項目:

- 氏名とユーザーカラー
- 作業時間、作業ログ回数
- 追加したタスク数、完了したタスク数、追加したサブタスク数
- タスク変更数、進捗投稿数、コメント・返信数
- 直近の代表的な活動（最大3件。日時、対象タスク、活動種別、短い内容）

活動がないメンバーも「活動なし」として表示し、「データがない」のか「表示から除外された」のかを曖昧にしない。カードは情報量を抑えた初期表示にし、詳細は展開できる構成とする。

特定メンバー選択時は、その人のカードを1件だけ詳細表示し、タスク別作業ログと活動履歴を確認できるようにする。「全員」と同じデータ定義を使い、画面によって数字が変わらないようにする。

## 5. データ/API設計

### 5.1 概要クエリ

Electron/Webで同じ `OverviewQuery` 契約を追加する。

- `assigneeId?: string | null`
  - `null` または省略: 全員
  - ユーザーID: 主担当またはサブ担当に含まれるタスク
  - 空文字: 主担当・サブ担当ともにいないタスク
- `includePrivate?: boolean`
  - 既存の閲覧レンズと一致させる。

サーバー側で対象タスク集合を先に1回確定し、サマリー、カテゴリ、期限、リスク、完了サブタスクをすべて同じ集合から計算する。クライアント側で全体集計を部分的に間引く方式は採らない。

### 5.2 担当者情報

`OverviewTaskItem` と `OverviewCompletedSubTaskItem` に表示用担当者情報を追加する。

- 主担当: ID、表示名、色
- サブ担当: ID、表示名、色の配列
- 完了サブタスク: サブタスク自身の担当者、および親タスク担当者

氏名変更や無効化後も孤児表示にならないよう、存在しないIDは `不明なユーザー`、担当なしは `未割り当て` と区別する。

### 5.3 活動データ

- 直近7日間の活動は既存 `progressDigestGet` のユーザー別集計を再利用する。
- 全員時は閲覧可能な対象メンバーIDを渡し、個人時は選択メンバーIDだけを渡す。
- `includePrivate` を概要クエリと同じ値にする。
- 現在の `worklogGetSummary(7)` によるログイン中ユーザー限定の取得は、概要から外すか、進捗ダイジェスト側へ統合する。
- 期間境界はローカル日付の「当日を含む直近7日」で統一し、概要カードと進捗レポートで同じ期間ラベルを表示する。

### 5.4 非同期状態

- 担当者を素早く切り替えたとき、古い応答で新しい表示を上書きしないよう要求世代またはキャンセル制御を入れる。
- タスク集計と活動集計の片方だけ失敗した場合は、成功した領域を残し、領域ごとのエラーと再試行を表示する。
- WebSocket等によるタスク更新時は現在の担当条件で再取得するが、短時間の連続更新はまとめて過剰リクエストを防ぐ。

## 7. 実装フェーズ

### Phase 1: 契約と集計の固定

- `OverviewQuery` と担当者付き応答型をElectron/Webで対称に定義する。
- サーバーの対象タスク抽出を共通化し、全員・主担当・サブ担当・未割り当て・非公開除外をDBレベルで検証する。
- Electron単独版で引数省略時の従来動作を維持する。

### Phase 2: 一覧簡素化と用語統一

- 複数選択UI、状態、ハンドラー、専用スタイルを撤去する。
- `ゴミ箱` のユーザー向け文言を全検索し、`アーカイブ`、`アーカイブ中`、`アーカイブ解除` 等へ統一する。
- 完全削除はアーカイブ表示中のみ可能という既存安全策を維持する。

### Phase 3: 担当者別概要

- 既存担当者フィルターを概要クエリへ接続する。
- ヘッダーの対象表示、各タスク・完了サブタスクの担当者表示を追加する。
- フィルター切替時の競合、読み込み、部分エラーを処理する。

### Phase 4: メンバー活動

- 進捗ダイジェストを再利用し、全員時のメンバーカードと個人時の詳細を実装する。
- 活動なし、未割り当て、無効ユーザー、非公開データの表示を整える。
- 既存の進捗レポートと共通化できる整形処理は抽出し、同じ活動を別定義で数えない。

### Phase 5: 回帰検証・文書・PR

- 自動検証、Electron/Webのproduction build、実ブラウザでの操作確認を行う。
- READMEと更新手順への影響を反映する。
- 差分レビュー、PR作成、CI確認、レビュー指摘対応後にマージする。

## 8. 検証計画

### 8.1 自動検証

- 型チェック: renderer、main/preload、server。
- production build: Electron版とWeb版。
- 一時DBによる概要集計テスト:
  - 主担当のみ、サブ担当のみ、両方、未割り当て。
  - 完了、進行中、期限超過、期限直近、アーカイブ。
  - 公開カテゴリ、非公開カテゴリ、カテゴリなし。
  - 同じタスクへ複数メンバーが活動した場合の担当集計と活動者集計の分離。
  - 無効ユーザーと活動なしユーザー。
- API契約テスト: 引数省略、全員、特定ID、空文字、不正ID、`includePrivate`。

### 8.2 手動検証

- 全員 → メンバーA → メンバーB → 未割り当てを素早く切り替え、最後に選んだ範囲だけが表示される。
- 一覧と概要で対象タスクが一致し、概要の全カード・各一覧で件数が矛盾しない。
- 主担当・サブ担当・未割り当ての名前表示と、人数が多い場合の省略表示を確認する。
- 全員時に全メンバーの活動カードがあり、個人時に選択メンバーだけになる。
- 「誰の担当タスクか」と「誰が操作したか」が別メンバーでも正しく表示される。
- 個人／全体レンズを切り替え、非公開カテゴリが全体概要・活動へ漏れない。
- 複数選択チェックと一括操作バーがなく、単一タスク操作・手動並べ替え・保存ビューは従来どおり動く。
- アーカイブ、復元、完全削除の動作を確認し、画面上に「ゴミ箱」の語が残っていない。
- 0件、長い氏名、多数メンバー、狭い画面、キーボード操作で崩れない。
- Electron単独版とWebサーバー版の両方で概要が表示される。

### 8.3 既存機能の回帰対象

- タスク作成・詳細編集・完了・アーカイブ・復元・完全削除
- タスク／サブタスクの並べ替えと期限追従
- ガント、カンバン、日別計画、概要、進捗タイムライン、進捗レポート
- タイマー、作業ログ、通知、リアルタイム同期
- 検索、カテゴリ・担当者フィルター、保存ビュー、個人／全体レンズ

## 9. 受け入れ条件

- タスク一覧に複数選択のチェックと一括操作が存在しない。
- 担当者フィルターを変更すると、概要の全タスク系指標・一覧が同じ対象へ切り替わる。
- 特定メンバーは主担当・サブ担当の双方で対象になり、未割り当ては主・サブ担当ともにいないタスクだけになる。
- 概要のタスクと完了サブタスクから担当者を判別できる。
- 全員表示では各メンバーの活動概要があり、活動がないメンバーも判別できる。
- 個人表示では、その人が担当するタスクの状況と、その人自身が行った活動を混同せず確認できる。
- 全体レンズでプライベートカテゴリの件数・題名・活動が漏れない。
- UI上に「ゴミ箱」の表記がなく、すべて「アーカイブ」系の表現になっている。
- Electron/Web双方の型チェックとproduction buildが成功する。
- 上記回帰対象に機能後退がなく、PRのCIとレビューが完了してからマージされる。

## 10. 今回は行わないこと

- 担当者・サブ担当の権限モデル変更。
- 新しい人事評価、ランキング、ノルマ機能。
- 活動量だけで生産性を評価するスコアリング。
- 進捗レポート全体の再設計。

## 13. タイマー計測中の表示安定化（追補）

- 原因: タイマーの1秒更新でAppが再描画されるたびに、絞り込み済みタスク配列が新しい参照になり、概要の取得処理が毎秒再実行されていた。
- 修正: タスク・サブタスク・カテゴリの実データから安定した更新キーを作り、実データ変更、担当範囲変更、閲覧レンズ変更、タイマー開始／停止時だけ概要を再取得する。
- UI整理: タスク一覧の新規「保存」ボタン、「全解除」ボタン、担当者の適用中チップを撤去する。既存の保存ビューがある場合の読み込み欄と担当者セレクトは維持する。
- 検証: 実ブラウザでタイマー計測中に約1.1秒間隔で6回確認し、概要の件数、読み込み状態、計測中表示が安定していることを確認した。修正版バンドルのコンソールエラーは0件だった。
